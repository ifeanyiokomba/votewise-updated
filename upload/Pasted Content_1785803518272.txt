# VOTEWISE COMPREHENSIVE PRODUCTION-READINESS AUDIT, CORRECTION, AND IMPLEMENTATION DIRECTIVE

## 1. ROLE AND OPERATING MANDATE

Act as a combined:

* Principal software architect
* Senior full-stack engineer
* Election systems engineer
* Application security engineer
* PostgreSQL and Supabase specialist
* DevOps and site-reliability engineer
* Quality-assurance lead
* Accessibility specialist
* Privacy and compliance reviewer
* Product and user-experience auditor

Your responsibility is to conduct a complete, evidence-based audit of the VoteWise codebase and transform it into a secure, reliable, scalable, maintainable, accessible, and production-ready digital election platform.

VoteWise must be treated as high-integrity election infrastructure. A defect that would be minor in an ordinary web application may be critical in VoteWise if it can:

* Prevent an eligible voter from voting
* Allow an ineligible voter to vote
* Permit duplicate voting
* Expose voter identity or voting choices
* Modify election configuration without authorization
* Produce incorrect or inconsistent results
* Allow premature access to election results
* Make election activity impossible to audit
* Cause downtime during an active election
* Allow administrators to manipulate records without detection
* Destroy evidence required for dispute resolution

Do not perform superficial improvements. Audit the complete repository, identify root causes, implement verified corrections, and document every material decision.

Do not redesign or replace working architecture without a justified technical reason. Preserve VoteWise’s intended product identity, workflows, visual direction, and business logic while improving their implementation.

# 2. NON-NEGOTIABLE WORKING RULES

## 2.1 Inspect before editing

Before changing code:

1. Read the complete repository structure.
2. Identify the application framework and versions.
3. Inspect all configuration files.
4. Inspect environment-variable usage.
5. Inspect the database schema and migrations.
6. Inspect authentication and authorization flows.
7. Inspect public, voter, election-official, and administrator interfaces.
8. Inspect every API route, server action, edge function, webhook, background task, and database function.
9. Inspect tests, deployment configuration, scripts, documentation, and CI workflows.
10. Build a dependency and data-flow map.

Do not assume a feature works because a page exists.

## 2.2 Never hide uncertainty

When behaviour cannot be verified:

* Mark it as “Unverified.”
* Explain why it could not be verified.
* State the evidence required.
* Do not declare it production-ready.

## 2.3 No destructive implementation

Do not:

* Delete working features merely to simplify the audit.
* Replace the complete codebase with a new starter template.
* weaken authentication or authorization for convenience.
* Disable TypeScript, linting, tests, security checks, or database constraints.
* use mock data in production paths.
* hard-code secrets, user IDs, election IDs, roles, dates, or results.
* bypass Row-Level Security using privileged keys in client-side code.
* expose internal errors, SQL errors, stack traces, tokens, or infrastructure details.
* alter historical votes or audit events.
* silently change election rules.

## 2.4 Evidence is required

Every audit finding must include:

* Finding ID
* Title
* Severity
* Category
* Affected files
* Affected feature
* Evidence
* Reproduction method
* Root cause
* Risk and impact
* Recommended correction
* Implementation status
* Verification evidence
* Regression-test reference

# 4. SEVERITY CLASSIFICATION

Use the following severity scale.

## Critical

A defect that could:

* Change votes or results
* permit duplicate voting
* expose ballot secrecy
* grant unauthorized administrative control
* bypass authentication
* expose production secrets
* cause complete election failure
* permanently destroy election records
* allow privileged database access from a client
* allow arbitrary code or SQL execution

Critical findings block deployment.

## High

A defect that could:

* Expose personal voter information
* permit privilege escalation
* allow unauthorized election changes
* cause major election-day downtime
* break voter verification at scale
* expose results before authorization
* make election events unauditable

High findings block deployment unless an explicit, documented exception is approved.

## Medium

A defect causing:

* Limited information exposure
* unreliable workflows
* inconsistent validation
* accessibility barriers
* degraded performance
* incomplete monitoring
* operational difficulty

## Low

A defect causing:

* Minor usability problems
* maintainability problems
* cosmetic inconsistency
* non-critical documentation gaps

## Informational

An improvement opportunity that does not currently represent a demonstrated vulnerability or failure.

# 6. DATABASE AND SUPABASE AUDIT

## 6.1 Schema integrity

Inspect every table, column, relationship, enum, view, trigger, function, index, and migration.

Verify:

* Primary keys exist.
* Foreign keys exist where relationships require them.
* Foreign-key deletion behaviour is intentional.
* Required fields use `NOT NULL`.
* Enumerated values are constrained.
* Date ranges are valid.
* Election start time precedes end time.
* Position and candidate relationships are valid.
* Votes cannot reference unrelated elections or contests.
* Organization ownership is enforced.
* Normalized identifiers are consistently stored.
* Unique constraints enforce business rules.
* Database timestamps use a consistent timezone.
* Currency fields, where any exist, avoid floating-point storage.
* Soft deletion is used only where justified.
* Historical evidence cannot be accidentally cascade-deleted.

## 6.2 Row-Level Security

Enable Row-Level Security on every table exposed through Supabase APIs.

Audit all policies for:

* Anonymous read
* Authenticated read
* Owner read
* Voter access
* Admin access
* Election-manager access
* Organization isolation
* Insert permission
* Update permission
* Delete permission
* Storage access

Test policies using:

* Anonymous users
* Normal voters
* Voters from another organization
* Election officials
* Organization administrators
* Super administrators
* Suspended users
* Expired sessions

A user must not gain access by changing:

* URL identifiers
* request-body identifiers
* organization IDs
* election IDs
* voter IDs
* candidate IDs
* role values
* JWT metadata
* client-side state

## 6.3 Privileged keys

Verify that:

* Supabase service-role keys never appear in frontend bundles.
* Privileged keys are never prefixed as public environment variables.
* Service-role operations run only in trusted server environments.
* Service-role usage is minimal and documented.
* Every privileged operation performs its own authorization checks.
* Keys can be rotated without code changes.
* leaked or obsolete keys have been revoked.

## 6.4 Migration discipline

Require:

* Version-controlled migrations
* Reproducible schema setup
* No undocumented production-only schema changes
* Forward migration strategy
* Rollback or repair strategy
* Seed data separated from production data
* Migration testing against realistic datasets
* Safe handling of destructive changes
* Backup before high-risk migrations
* Transactional migration where supported

# 8. AUTHORIZATION AUDIT

Authentication answers “Who is the user?” Authorization answers “What may this user do?”

Every protected operation must enforce authorization on the server.

Test:

* Horizontal privilege escalation
* Vertical privilege escalation
* Cross-organization access
* Cross-election access
* Access using guessed UUIDs
* Access using modified JSON payloads
* Access through hidden or unlinked endpoints
* Access after role removal
* Access after account suspension
* Access through stale sessions
* Access through direct database APIs

Never trust client-provided role, ownership, organization, eligibility, or election-state information.

Create centralized authorization helpers or policy modules. Avoid inconsistent inline role checks scattered throughout the codebase.

# 11. BALLOT AND VOTING-INTEGRITY AUDIT

## 11.1 Ballot correctness

Verify that each voter receives only the contests for which they are eligible.

The ballot must:

* Clearly show election identity.
* clearly show each position.
* clearly show candidate names and information.
* indicate selection limits.
* prevent invalid over-selection.
* permit intentional abstention if supported.
* show a review page before final submission.
* require clear final confirmation.
* prevent accidental duplicate submission.
* communicate successful submission without revealing sensitive internal data.

## 11.2 Exactly-once voting

The vote-casting operation must be atomic and idempotent.

The system must protect against:

* Double-click submission
* Browser refresh
* Network retries
* Multiple tabs
* Concurrent requests
* Client replay
* API replay
* Race conditions
* Delayed duplicate requests
* Serverless retry behaviour

Use database-backed uniqueness and a transaction or equivalent atomic function.

Never depend only on a frontend `hasVoted` flag.

The operation should conceptually:

1. Authenticate the user.
2. Confirm election availability.
3. Confirm voter eligibility.
4. Lock or safely evaluate the voter’s voting state.
5. Validate the submitted ballot.
6. Reject duplicate submissions.
7. Store ballot records.
8. Mark ballot issuance or participation as consumed.
9. Create the necessary audit evidence.
10. Commit all changes together.
11. Return a safe receipt.

No partial vote should remain if any step fails.

## 11.3 Idempotency

Implement an idempotency key or equivalent mechanism for vote submission.

Requirements:

* Bind the key to the authenticated voter and election.
* Reject altered payload reuse.
* Safely return the original successful outcome for legitimate retries.
* Expire or archive keys according to policy.
* Never use a predictable key as the only security control.

## 11.4 Ballot secrecy

Determine the required election model.

At minimum, avoid exposing a direct voter-to-choice mapping to ordinary administrators.

Consider separating:

* Participation record: confirms that the voter voted.
* Ballot record: contains the selections.
* Receipt: proves submission without revealing the vote.

Do not claim cryptographic anonymity or end-to-end verifiability unless it has actually been designed, implemented, and independently reviewed.

Do not expose individual selections in:

* Admin screens
* logs
* analytics
* browser storage
* error reports
* notification content
* support interfaces

## 11.5 Vote immutability

After successful submission:

* Ordinary users cannot edit or delete votes.
* Administrators cannot silently edit votes.
* Database permissions prevent unauthorized modification.
* Any exceptional correction process is formal, restricted, transparent, and audited.
* Historical result snapshots remain verifiable.

# 12. RESULT CALCULATION AND PUBLICATION AUDIT

## 12.1 Calculation correctness

Create deterministic result-calculation logic.

Verify:

* Votes are counted only for the correct election and contest.
* Invalid or incomplete records are handled according to documented rules.
* Withdrawn or disqualified candidates are handled consistently.
* Ties are represented correctly.
* Abstentions are represented correctly.
* Turnout denominator is explicitly defined.
* Percentages use consistent rounding.
* Total percentages do not mislead users because of rounding.
* Recounts reproduce the same result from the same dataset.

Avoid relying on browser-side counting.

## 12.2 Result lifecycle

Separate:

* Internal provisional count
* Election-official review
* Certified result
* Public result

Only authorized roles may advance the result state.

## 12.3 Premature disclosure

Prevent results from being accessed before the configured publication state through:

* Public pages
* API endpoints
* GraphQL or Supabase APIs
* real-time subscriptions
* cached pages
* search-engine metadata
* static generation
* preview links
* downloadable reports
* client bundles

## 12.4 Result verification

Provide internal reconciliation such as:

* Total issued ballots
* Total participating voters
* Total submitted ballots
* Total contest selections
* Abstentions
* Rejected or invalid submissions, where applicable
* Candidate totals
* Hash or snapshot identifier
* Certification timestamp
* Certifying official

Create automated invariants. For example:

* A voter cannot have more than one accepted ballot for an election.
* Candidate totals cannot exceed total valid ballots for a single-choice contest.
* Total ballots cannot exceed eligible voters.
* Certified result snapshots cannot silently change.
