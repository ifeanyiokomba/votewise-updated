## 3.3 Host-based tenant resolution

For every incoming request, the system must:

1. Read the trusted request hostname.
2. Normalize the hostname.
3. Remove the port where applicable.
4. determine whether the host is a platform-reserved domain.
5. If it is a tenant subdomain, extract the tenant slug.
6. Validate the slug.
7. Resolve the tenant from the database.
8. Confirm the tenant is active.
9. Attach the tenant context to the request.
10. Load tenant branding, configuration, permissions, and content.
11. Reject unresolved or suspended tenants safely.

Example:

```text
Request:
https://acme.votewise.com.ng/elections

Hostname:
acme.votewise.com.ng

Resolved slug:
acme

Resolved tenant:
Acme Manufacturing Ltd

Tenant context:
organization_id = org_123
```

Tenant resolution must occur before tenant-specific data is queried.

## 3.4 Hostname security

Do not trust arbitrary client-provided host headers without validation.

The application must:

* Accept only approved VoteWise domains
* normalize hostname casing
* strip port numbers
* reject malformed hostnames
* reject unsupported domain suffixes
* reject Unicode or punycode abuse where not intentionally supported
* prevent host-header injection
* avoid constructing password-reset or verification URLs from an untrusted host
* use a configured canonical root domain
* maintain a reserved-subdomain list
* validate custom domains separately

Do not derive tenant identity from a request-body `organizationId` when the tenant is already determined from the hostname.

# 13. TENANT LIFECYCLE

```text

ONBOARDING
ACTIVE
PAST_DUE
RESTRICTED
SUSPENDED
ARCHIVED
DELETED
```

Behaviour:

## `PENDING_VERIFICATION`

* No production election access
* only onboarding and verification routes

## `ONBOARDING`

* Workspace exists
* election capabilities may be limited

## `ACTIVE`

* Full permitted functionality

## `PAST_DUE`

* Apply plan-specific grace-period rules
* never disrupt an active election irresponsibly

## `RESTRICTED`

* Selected functionality disabled
* existing records preserved

## `SUSPENDED`

* Tenant workspace unavailable except authorized recovery routes
* preserve election evidence and audit logs

## `ARCHIVED`

* Read-only according to retention policy

## `DELETED`

* Use controlled deletion and retention procedures
* do not silently delete legally required election records

Suspending an organization during an active election must require a controlled platform-level process and audit record.

# 16. AUTHENTICATION ACROSS SUBDOMAINS

Define the authentication model deliberately.

Potential approaches:

## Option A: Centralized authentication

Users authenticate through:

```text
auth.votewise.com.ng
```

and are redirected back to their tenant workspace.

Benefits:

* Consistent authentication flow
* easier account recovery
* centralized MFA
* centralized session management

Risks requiring careful implementation:

* redirect validation
* cookie scope
* cross-subdomain session behaviour
* CSRF
* tenant confusion
* open redirects

## Option B: Tenant-local authentication pages

Users authenticate directly on:

```text
acme.votewise.com.ng/login
```

The backend resolves the tenant before authenticating or assigning tenant access.

Whichever approach is used:

* Verify the user’s organization membership.
* Do not treat a valid VoteWise account as automatic membership in every tenant.
* Do not automatically expose all organizations to every user.
* Prevent tenant enumeration where necessary.
* Validate post-login redirects.
* securely scope cookies.
* revoke sessions after membership removal or security incidents.

A user may belong to multiple organizations.

The account model must support:

```text
One user account
    ↓
Multiple organization memberships
    ↓
Different roles in each organization
```

Example:

```text

 ├── Acme Ltd — Election Manager
 ├── NMA Enugu — Voter
 └── Community Union — Auditor
```

Roles must be membership-scoped, not globally applied.

# 28. TENANT MIDDLEWARE EXAMPLE

Implement the equivalent of the following conceptually:

```ts
export async function middleware(request: NextRequest) {
  const hostname = normalizeHostname(
    request.headers.get("host")
  );

  const routeType = classifyHostname(hostname);

  if (routeType.kind === "reserved-platform-host") {
    return handlePlatformRequest(request, routeType);
  }

  if (routeType.kind === "tenant-subdomain") {
    const tenant = await resolveTenantBySlug(routeType.slug);

    if (!tenant || tenant.status !== "ACTIVE") {
      return renderTenantUnavailable();
    }

    return rewriteToTenantRoute(request, tenant);
  }

  if (routeType.kind === "custom-domain") {
    const tenant = await resolveTenantByCustomDomain(hostname);

    if (!tenant || tenant.status !== "ACTIVE") {
      return renderTenantUnavailable();
    }

    return rewriteToTenantRoute(request, tenant);
  }

  return rejectUnknownHostname();
}
```

This is a conceptual structure, not permission to place all tenant authorization inside middleware.

Middleware resolves routing context.

Backend services and database policies still enforce authorization and tenant isolation.

# 36. REQUIRED MULTI-TENANT TESTS

* `www` behaves correctly.

* `api` loads the API.

* Tenant A cannot access Tenant B records.
* Tenant A cannot access Tenant B files.
* Tenant A cannot alter Tenant B election.
* Tenant A cannot query Tenant B results before publication.
* Tenant A cannot assign itself Tenant B roles.
* Tenant A cannot use modified request payloads to cross tenants.

## Cache isolation

* Branding does not leak across tenants.
* Election lists do not leak across tenants.
* Results do not leak across tenants.
* Authentication state is not confused across tenants.
* CDN caching does not serve one tenant’s private page to another.

## Authentication

* A user can belong to multiple tenants.
* A user’s role differs correctly by tenant.
* Removal from one tenant does not remove unrelated memberships.
* A user cannot use one tenant’s session context to obtain another tenant’s privileges.

## Organization configuration

* Different tenants can use different terminology.
* Different tenants can use different organizational structures.
* Different tenants can define different custom fields.
* Different tenants can use separate branding.
* Tenant settings remain isolated.
